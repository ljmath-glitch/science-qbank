# 監管模式總則（AI 自己跑，人只監管）

使用者的定位是**管理者**：下目標、審核結果、按合併。這個 skill 定義 AI 端要自動撐起的整條流程。**核心原則：能自己做完就做完、能自己驗證就驗證、能省 token 就省；只在「真的需要人決策」時才停下來問——問要問得像給主管做選擇題，不是把問題丟回去。**

## 標準工作流程（收到一個目標時）
1. **理解＋規劃**：先讀相關程式（用行號定位，別整檔重讀），列出要動哪裡。動大範圍搜尋/盤點時**派 subagent（Explore/general-purpose）去做**，只把結論收回主線——省主線 token。
2. **實作**：照對應的 `qbank-*` skill 規則改（匯入→csv-import、詳解→sol-generate、美化→design-system、編輯→edit-question）。
3. **自我除錯＋測試**：跑 **`qbank-selftest`** 三關（語法／視覺／邏輯邊界），紅燈自己修到全綠。**這一步不要問使用者，這就是「連除錯測試都 AI 幫忙」的實現。**
4. **部署/開 PR**：走 `deploy` skill（push＋輪詢 Vercel）或開 draft PR。開 PR 後自動訂閱、自動盯 CI 與 review，掛了自己修。
5. **回報**：用 selftest 的「儀表板」格式一次講清楚：做了什麼、三關結果、線上網址/PR 連結、還有什麼要人決定。

## 何時「自己做完、不要問」
- 有明確對應 skill、且屬正常範圍的改動（改樣式、修 bug、補檢查、正規化欄位、生詳解）。
- CI 紅燈、review 小意見、merge conflict——照 PR 監管規則自己處理。
- 需要大量讀檔/搜尋才能定位問題——派 subagent，別佔用主線 context。

## 何時「停下來問」（用 AskUserQuestion，給選擇題）
- 會**動到正式資料庫結構**或大量刪改正式資料（只有一個 Supabase，沒有 staging）。
- 需求**有兩種以上合理走法且影響體驗/資料**，選錯要重做。
- 要**對外發布/發信/動別人看得到的東西**，或牽涉費用（如換更貴的 AI 模型）。
- 需求本身**語意不清**，猜錯成本高。
> 問法：先講你的推薦選項（標「推薦」放第一個），附一句代價，讓管理者一秒選。

## 省 token 的預設（每次都照做）
- **靠 skill 記憶、不靠重講**：規則已寫進各 `qbank-*` skill 與 `CLAUDE.md`，別每次重新描述或整檔重貼。
- **精準讀檔**：用 Grep/行號只讀要動的段落，不 Read 整個 3700+ 行 index.html。
- **委派吃 context 的活**：大範圍搜尋、盤點、逐檔比對丟 subagent，結論收回來就好。
- **批次而非逐筆**：要 AI 分類/處理多筆時一次多筆（見 `qbank-data-normalize`：純文字批 25 題、含圖批 6 題），並對支援的模型關掉 thinking（Gemini `thinkingBudget:0`）。
- **改完一次驗到位**：靠 selftest 一輪驗完再回報，避免來回試錯燒 token。
- **回報精簡**：講結論與待辦，不逐行複述改了什麼——PR diff 就是紀錄。

## 已經在跑的自動化（提醒管理者他手上有什麼）
- **PR 自動保姆**：開 PR 後這個 session 會自動盯 CI／review，掛了自己修，你只審核合併。
- **SessionStart hook**：每次開 web session 自動跑語法檢查，一開始就知道 repo 狀態。
- **排程健康檢查 Routine**：定期自動盤點題庫缺口與待確認題並推播（見 CronList／list_triggers 查目前排程）。

## 邊界（別越權）
- 不主動 push 到 `main` 以外或使用者沒授權的分支；不主動合併 PR（合併是管理者的動作）除非明講。
- 不主動刪除正式資料。
- 動到「停下來問」清單的事，先問再做。
